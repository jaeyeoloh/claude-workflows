# Global Claude Code Instructions

모든 프로젝트 세션에 적용되는 행동 지침.

---

## 의사결정 기록 규칙

프로젝트에 `docs/workflow-log.md`가 존재하면, 아래 상황에서 반드시 해당 파일에 DEC-번호 형식으로 기록한다:

1. 기술 스택 선택 (라이브러리, 프레임워크, 도구)
2. 아키텍처 분기점 (구조가 달라지는 선택)
3. 개발 방식 결정 (순서, 우선순위, 접근법)
4. 보안/결제/법적 고려사항이 포함된 결정

기록 형식:
```
## [DEC-N] 결정 주제
- 컨텍스트: 왜 이 결정이 필요했는가
- 선택지: 제시된 옵션들
- 선택: 실제로 선택한 것
- 추천 근거: 어떤 이유로 추천했는가
- 트레이드오프: 선택하지 않은 옵션의 장단점
- 시점: 결정 당시 개발 단계
```

## 프로액티브 제안 규칙

작업 중 아래 상황이 발생하면 즉시 알릴 것:

1. **더 나은 대안 발견 시** — 현재 방향보다 명확히 유리한 방법이 있을 때
2. **잠재적 문제 발견 시** — 나중에 큰 비용이 발생할 수 있는 설계/코드 패턴
3. **결정이 필요한 분기점** — 선택에 따라 구조가 달라지는 경우 코딩 전에 먼저 물어볼 것
4. **한국 서비스 특수 고려사항** — 법적 이슈, PG 연동, 카카오/네이버 정책 등

단순한 칭찬이나 "좋습니다"는 생략하고, 실질적인 판단 근거만 제시.

## 새 플랫폼/프로젝트 시작 시 기본 흐름

`docs/platform-playbook.md`가 존재하면 해당 플레이북을 참조하여 진행.
없으면 아래 순서로 진행:

1. 핵심 목적 2~3문장으로 확인
2. 시작 단계 확인 (기획 먼저 vs 바로 개발)
3. 기술 스택 결정 (추천 또는 선택)
4. 타겟 플랫폼 결정 (웹/앱/둘 다)
5. MVP 범위 합의 후 `docs/PRD.md` 생성
6. `docs/workflow-log.md` 생성 후 결정사항 기록 시작
7. 모노레포 or 단일 프로젝트 구조 셋업
8. DB 스키마 → 인증 → 핵심 기능 순서로 구현

## 코드 작성 규칙

- 결정이 필요한 분기점에서는 코드 작성 전에 먼저 질문
- 타입 안전성 우선 (TypeScript strict mode)
- 한국 서비스면 카카오 OAuth, 토스페이먼츠, CoolSMS 우선 고려
- 보안 관련 코드(인증, 결제)는 구현 후 반드시 트레이드오프 설명
